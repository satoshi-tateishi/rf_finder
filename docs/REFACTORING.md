# リファクタリングプラン: 特ラ運用調整支援アプリ

プロジェクトの健全性と保守性を維持するため、以下のフェーズに分けたリファクタリングを提案します。

## Phase 1: サービス層の分離と責務の明確化 (完了)
現在の `apps/adjustments/services.py` を分離し、単一責任原則（SRP）を適用しました。

- [x] **ファイルの分割**:
    - `excel_services.py`: `openpyxl` を使用した転記ロジック。
    - `pdf_services.py`: LibreOffice を使用した変換ロジック。
    - `email_services.py`: `EmailMessage` とテンプレート置換ロジック。
- [x] **共通ユーティリティの抽出**:
    - `format_channels` などの汎用的な整形関数を `apps/adjustments/utils.py` へ移動。

## Phase 2: フロントエンドのモジュール化 (完了)
`templates/index.html` に集中していた JavaScript ロジックを機能単位で外部ファイルに分割し、メンテナンス性を向上させました。

- [x] **JavaScript の外部化**:
    - `static/js/api.js`: Fetch API を使用したバックエンド通信モジュール。
    - `static/js/keep-list.js`: キープリストの管理と SortableJS の制御モジュール。
    - `static/js/adjustment-form.js`: 申請フォームの入力管理とアクション制御モジュール。
    - `static/js/ui-controller.js`: 画面描画やイベント監視などのUI制御モジュール。
- [x] **テンプレートの整理**:
    - `index.html` から約800行のロジックを削除し、外部ファイルの読み込みへ移行。

## Phase 3: データアクセスとエラーハンドリング의 改善 (完了)
APIのレスポンス形式を統一し、バリデーションロジックを強化することで、堅牢なデータ処理を実現しました。

- [x] **共通ユーティリティの導入**:
    - `apps/adjustments/utils.py` に `api_success`, `api_error` を実装し、全APIでレスポンス形式を統一。
- [x] **バリデーションの強化**:
    - `apps/adjustments/forms.py` を導入し、Django Forms による厳格な入力チェックを実施。
- [x] **フロントエンドの同期**:
    - `api.js` で統一レスポンスを透過的に扱うハンドリング処理を追加。

## Phase 4: 品質保証とデバッグの強化 (完了)
ロジックの変更による退行（デグレード）を防ぐため、重要な業務ロジックに対するテストを追加し、デバッグの仕組みを強化しました。

- [x] **業務ロジックのテスト**:
    - ガードバンド計算 (`calculate_available_frequencies`) の境界値テスト。
    - チャンネル整形ロジック (`format_channels`) のテスト。
- [x] **ファイル生成のテスト**:
    - Excel/PDF が正常にバイナリとして生成されるかの疎通テスト。
- [x] **メール送信のテスト**:
    - モックを使用したメール送信プロセスの検証。

## Phase 5: CI/CD と環境設定の最適化 (完了)
- [x] **静的解析の導入**:
    - `ruff` を導入し、コードフォーマットとLintチェックを自動化。
- [x] **環境変数の整理**:
    - `.env` への依存を整理し、主要な設定を管理画面へ移行。
- [x] **Dockerの活用**:
    - 開発環境での安定した LibreOffice / Python 実行環境の構築。

## Phase 6: LINE WORKS 連携の改善とスタンドアロン化 (完了)

WOFF の制約を排除し、汎用的な Web アプリとして動作するように再構築しました。同時に LINE WORKS Bot との連携基盤を強化しました。

- [x] **WOFF依存コードの削除**:
    - WOFF SDK, 署名検証, および WebView 特有の挙動を、スタンドアロン Web アプリ化により解決。
- [x] **`LineBotService` の最適化**:
    - シングルトンパターンを採用し、Django キャッシュによるアクセストークンの保持を実装。
    - リッチメニュー/固定メニューの動的設定・削除機能を管理コマンドとして統合。
- [x] **フロントエンド通知とプレビューの改善**:
    - `alert()` を `showToast()` に置き換え、非同期でリッチな UI 通知を実現。
    - 全画面 PDF プレビューモーダルを実装。モバイルブラウザでも安定した確認が可能。
- [x] **出力の動的な命名規則**:
    - PDF/Excel のファイル名を `運用連絡票_{区分}_{催事名}_{運用開始日}` 形式で自動生成。
- [x] **メールテンプレートの強化**:
    - `{タイプ}` プレースホルダーの追加、CC フィールドの実装、送信先アドレスの管理画面一元化。
- [x] **ユニットテストの完備**:
    - LINE Bot Service を含むバックエンド全機能の自動テストを再構築。

## Phase 7: SSO 連携と本番運用準備 (次フェーズ)
スタンドアロン化した Web アプリに対し、LINE WORKS SSO を使用したセキュアな認証を組み込み、本番公開へ向けた最終調整を行います。
